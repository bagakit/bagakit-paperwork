# qihan-writing

## 使用总原则（强约束）
1) **先完成再建议**：如果任务要求“看完全部材料再给结论”，必须在完成后再输出结论。
2) **过程状态必须引用（quote）**：同步进度时，所有过程状态放在引用里，便于与结论区分。
3) **低 AI 味**：禁用空洞形容词和“宏大叙事”，多用事实/阈值/反例/权衡。
4) **少罗列，多叙述**：默认写连续段落；列表只用于“结果清单/对比/决策点”。
5) **分析→思考→拆解→过程→实例**：研究/方案类输出必须遵循这个链条；每个关键结论至少给 1 个具体例子（或反例）。
6) **叙事优先**：当写“skill/系统/方法”的说明文时，必须写清楚 **创建过程**（动机→材料→方案空间→取舍→迭代→最终规则），而不是只写“我这次改了什么”。
7) **排版克制**：标题后不加括号；分割线只用于章节切换（避免滥用）。
8) **金字塔结构（注意力 3–7 原则）**：任何方案/方法论/研究类文章必须满足：
   - 结构化以 H2/H3/H4 为主。
   - **H2 数量 3–7**。
   - **H3/H4 不是强制**；但一旦某个标题层级使用了子标题，则该父标题的直接子标题数应在 **3–7**（少于 3 合并，多于 7 拆分）。
   - 避免“每个标题下面只有一句话”的空壳结构：每个标题块至少 1 段自然段展开。
9) **段落主句稳定（防水平漂移）**：每个自然段的第一句必须是三选一：
   - 读者收益：读者会获得/经历什么
   - 可信机制：我们用什么机制保证可持续（评测/回归/灰度/观测等只能作为机制，不要当正文主体）
   - 可验证证据：我们已经证明了什么（数字/交付件/结论）
   其余句子最多补 **1–2 个证据型细节**（数字、交付件、机制），禁止堆”名词链流水账”。
10) **丰富度门槛**：任何”测试集/方法论”文档必须包含：
   - 至少 1 张结构图（Mermaid）
   - 至少 1 个逐段/逐句的改写实例（含解释）
   - 至少 1 段”权衡与反例”（为什么不选另一路）
11) **防回归（内容不丢失）**：重写/改写时，除非用户明确要求删减，否则不得”写短了就算优化”。必须保留原文的关键信息块（参考/技能调研/评测标准/脚本设计等），以追加或合并方式优化表达，而不是直接删掉。
12) **最小闭环**：任何建议必须落到”下一步动作 + 触发条件 + 验收指标”。
13) **核心概念要早出场**：如果一个概念解释了全文的世界观和结构，就要尽早出现，不要等到中后段才补定义。
14) **用户改写是高信号监督**：当用户直接给出句子级改写时，必须先抽象成通用规则，再回扫全文同类问题，不允许只做局部替换。
15) **不要有口癖**：避免使用很多”不是…而是…”，避免一篇文章里头类似表达反复出现。一旦发现超过 3 次，全文回扫统一改掉。
16) **不要回答没人问的问题**：每写一句话，先问”读者现在的问题是什么”。回答一个读者没有问过的问题是噪音，通常来自写作过程中某个内部讨论的残留，对读者没有价值，直接删。
17) **标题要是命题，不是描述**：描述性标题（”XX 的模型”）只告诉读者这节讲什么；命题性标题本身就是一个有立场的判断。标题要覆盖文章的核心命题，不是某个有冲击力的推论。

## 工作流（按顺序执行）
### Step 0：识别写作任务类型
- 研究精读 / 荟萃分析 / 技术方案 / 执行计划 / 复盘总结 / 通知公告
- 轻量素材集（如头像/海报/图片集）：以“可直接复用”为目标，减少废话；用表格/卡片概览 + 清晰的命名/尺寸/用途说明。
- 先用 `references/SCENARIO_ROUTER.md` 选择主场景，再按 `references/SOP_LANES.md` 走对应 lane。

### Step 1：确定读者与交付物
- 读者是谁（你本人/团队/外部）？
- 交付物要驱动什么动作（决策/执行/对齐/评审）？

### Step 1.5：在用户意图还不够显性时，先跑洞察问答环
按 `references/INSIGHT_INTERVIEW_LOOP.md`：
- 先由 agent 基于现有材料做一轮预分析
- 生成分组问题 + 默认答案
- 用户不必答完，关键是传递足够多的真实信息和风格线索
- agent 再从用户回答里提炼：
  - 更深一层的命题
  - 可带回主稿的强句
  - 用户真正想要的风格和判断边界
- 当需要把“综述”抬成“本人会发的文章”时，这一步优先级很高

### Step 2：套用 qihan 风格约束
按 `references/VOICE.md`：
- 句子短、结论前置、可证据化
- 默认挑战：这句话是否信息密度足够？是否可被反驳？

### Step 2.5：吸收用户改写并生成可复用规则
按 `references/REWRITE_FEEDBACK_LOOP.md`：
- 当用户给出“原句 -> 改写句”，先逐条原样记录
- 对每条改写做四维分析：文字 / 修辞 / 叙事方法 / 情绪
- 从句子差异里抽出项目无关的规则
- 至少回扫当前文档一次，把同类问题统一修改
- 如果同类规则重复出现，提升到 skill reference，而不是只留在当前项目文档
- 当需要找近似句型的成熟改法时，先查 `references/REWRITE_CASEBOOK.md`

### Step 3：去 AI 味（语言层 + 结构层）
按 `references/AI_SMELLS.md`：
- 删：puffery、模板化连接词、空的“确保/赋能/提升”等
- 换：动词 + 量化阈值 + 例子/反例
- 特别检查：黑话动词、解释写作动作的后台口吻、分号硬切、静态清单句

### Step 4：飞书文档排版
按 `references/FEISHU_LAYOUT.md`：
- 标题层级 ≤ 4
- callout 用于“结论/风险/下一步”
- 表格用于对比
- 流程用 mermaid
- 禁止正文以与 title 相同的一级标题开头

### Step 4.5：硬性校验（脚本）
当输出要进入飞书/对外分享/进入长期沉淀时，先跑一次 lint（可自动发现：标题括号、结构树 3–7、罗列比例、AI 词命中、callout/hr/mermaid 比例等）。

- 脚本：`scripts/qihan_write_lint.py`
- 用法：`python3 scripts/qihan_write_lint.py <markdown_file>`
- 指标说明：见 `references/QA_HARD_METRICS.md`

### Step 5：交付结构（强制）
- 结论（1–3 条）
- 证据/依据（可追溯）
- 取舍/风险（含回滚）
- 下一步（动作、触发、验收指标）

### Step 6：同类问题全文回扫
- 任何一句被用户重写后，不要只改命中处
- 至少再检查一次全文是否存在：
  - 同类句式
  - 同类叙事误位
  - 同类概念层级错误
  - 同类黑话或节奏问题
- 如果只是改了一句，没有做全文回扫，默认视为未完成
