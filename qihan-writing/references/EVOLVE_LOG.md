# qihan-writing Evolve Log

## 2026-03-23

### 输入来源

- 一次真实技术长文写作任务中的连续多轮改写
- 用户直接给出的句子级改写
- 配套写作计划中沉淀下来的原句对照、风格规则和整篇回扫要求

### 这轮新确认的规则

1. **用户改写是高信号监督**
- 不能只把它当普通润色意见。
- 必须先记录原句和改写句，再分析差异，再提升成通用规则。

2. **局部反馈必须触发全文回扫**
- 用户点一句，不代表只改一句。
- 真正高质量的写作改稿，要顺着这句回扫全文里的同类问题。

3. **第一人称不是越少越好**
- 该减少的是解释写作动作的“我”。
- 该保留的是个人世界观、个人下注、个人实践轨迹、无硬证据强判断里的“我”。

4. **核心概念应更早出场**
- 如果一个概念解释了全文结构和世界观，就不能放到后面当补充说明。
- 例如 `Build` 这种概念，应尽早进入正文主轴。

5. **机制写法优先于动作清单**
- 比起罗列“分享、评论、补充、修正”，更应该说明这些动作共同构成了什么过程。

6. **少黑话，少分号**
- “挂起 / 钉死 / 挂出来”这类词在成文里经常显得虚。
- 分号往往掩盖了句间关系没写清，优先改成更自然的因果或递进。

7. **当一个机制既有约束又有机会，要写两面**
- 只写约束，会显得规训。
- 同时写出机会、动力装置和文化土壤，文章会更有生长感。

8. **洞察问答环是高价值写作机制**
- 先让 agent 基于材料预分析，再让用户部分回答，最后回收强句、风格边界和更高命题。
- 它解决的不是“信息不够”，而是“用户真正的判断还没完全显性化”。

9. **写作已经足够适合场景化和 SOP 化**
- 规则层和样本层已经比较强，但如果没有场景路由和 SOP 分道，执行时仍然容易“选错写法”。
- 真正高质量的 skill，不只要告诉模型“怎么写”，还要先告诉它“当前究竟在做哪一类写作任务”。

10. **全文回扫规则应进入 eval backlog**
- “用户给一句改写，skill 自动让全文一起变好”不是体验细节，而是 skill 是否真正进入高质量协同的关键门槛。
- 这条规则已经足够明确，应该作为后续优先补成 eval 的方向。

11. **综述写作的证据层也值得单独抽象**
- 样本口径、术语表、inventory、缺失样本边界、链接可迁移性，这些不是某个项目的偶然细节，而是综述类文稿进入“可审计状态”后的共性要求。
- 这意味着写作 skill 不只要管文风，还要管 evidence architecture。

## 2026-04-07

### 输入来源

- 一次技术架构文档的从零写作与多轮改写任务（spec-model.md）
- 用户直接给出的句子级改写和逐轮反馈
- 对"周李奇翰风格"的系统性模仿与校正

### 这轮新确认的规则

1. **具体场景代替泛化断言开头**
   - "大多数人会…"这类开头让读者是旁观者，没有代入感。
   - 换成一个有名字、有细节的具体场景，读者立刻变成当事人。
   - 场景要有具体系统名、具体需求，不能只是"假设有一个项目"。

2. **泛化背书要换成直接判断**
   - "任何在大型系统里工作过的工程师都知道"是在用群体权威代替自己的判断。
   - 直接删掉这层，把判断内容本身写出来。
   - 群体共识不等于判断正确，两者不能互相替代。

3. **目标宣言要说"是什么"，不说"为什么重要"**
   - "这是…领域，也是…关键"是在给读者解释重要性，有说教感。
   - 直接说定位是什么，让重要性从定位本身里透出来。
   - 凡是出现"这是…无法解决的领域 / 这是…最重要的事"，先检查能不能删掉。

4. **不要回答没人问的问题**
   - 每写一句话，先问：读者现在的问题是什么？这句话在回答这个问题吗？
   - 回答没人问的问题是噪音，通常来自写作过程中某个内部讨论的残留。
   - 典型例子："入口文件叫 index.md 还是 README.md，不是核心问题"——读者根本没问过这个。

5. **标题要是命题，不是描述**
   - 描述性标题（"XX 的模型"）只告诉读者这节讲什么。
   - 命题性标题本身就是一个有立场的判断，读者看到标题就知道作者的角度。
   - 标题要覆盖文章的核心命题，不是某个有冲击力的推论。

6. **引入更高层级的宿主概念拔高论点**
   - 当一个判断可以被某个已有理论框架命名时，引入这个框架能让论点更有说服力。
   - 例：用 Polanyi 的隐性知识概念解释"为什么成熟系统的约束无法被文档化"。
   - 例：用 Conway 定律解释"为什么按团队划分的目录对 Agent 有额外认知负担"。
   - 引入的概念要真正推进判断，不是装饰。

7. **"不是…而是"是口癖，要系统性消除**
   - 这个句式是 AI 写作的典型腔调，用否定来强调肯定，绕了一圈。
   - 直接说肯定的那半句更干脆。
   - 一篇文章里这个句式出现超过 3 次，就要全文回扫统一改掉。

8. **反直觉的判断要显式标出来**
   - "残缺但稳定的协议，比完整但会变的协议更有用"——这类判断如果不显式说出来，读者会错过。
   - 用"这里有一个反直觉的判断"或直接加粗，让读者知道这是文章的核心洞察之一。

9. **结尾回到开头的具体场景，形成闭环**
   - 开头用具体场景切入，结尾用同一个场景作为验收标准，文章首尾闭合。
   - 比抽象的责任宣言（"工作现场的维护责任，在我们这里"）更有力量。

### 对下一轮 evolve 的建议

1. 补更多高质量“原句 -> 改写句”样本，覆盖：
- 标题
- 段首句
- 结尾收束句
- 机制定义句

2. 如果同一类黑话或后台口吻持续出现，考虑把 warning 提升成更强的门禁。

3. 如果用户长期用同一套句子改法，可以考虑增加一个轻量脚本，自动生成“改写样本表”，减少手工归纳成本。
4. 如果 casebook 持续增长，下一步可以为每条 case 增加标签和 failure_mode，形成更清晰的写作问题索引。
5. 如果 insight interview loop 被频繁使用，下一步可以补一组“洞察问答”模板与 failure mode，对问题设计本身做评测。
6. 如果场景路由稳定，下一步应该把每个 scenario 的 pass/fail fixture 补起来，让写作 skill 从“强经验”继续长到“强 eval”。
7. 如果 evidence architecture 在综述场景里反复触发，下一步应补本机绝对路径、sample frame wobble、缺失样本边界的脚本化检查。
