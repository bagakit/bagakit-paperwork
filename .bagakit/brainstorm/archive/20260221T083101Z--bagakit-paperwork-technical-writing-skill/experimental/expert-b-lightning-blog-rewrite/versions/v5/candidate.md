# Brainstorm 的自解释系统与专家论坛评审系统

> Coding 的尽头是项目管理

## 一、问题诊断

### 1) 为什么这个问题现在必须解决

当协作从“一个人连续写作”变成“多人跨会话推进”时，brainstorm 的失效成本会急剧上升。

在单人场景中，隐性上下文可以靠记忆补齐；在多人场景中，隐性上下文会直接变成执行偏差。比如 A 在周一会议里把“先做结构改造”当作结论，B 周三接手时却把它理解成“先做文风润色”，最终两人都在正确执行“自己理解的版本”。

这个阶段不再是写作技巧问题，而是决策接口问题。

### 2) 失败通常发生在哪三个位置

第一类失败是结构漂移。  
同一件事在不同轮次被命名为“计划”“方案”“讨论结果”，没有稳定文件契约，导致历史不可复用。

第二类失败是证据漂移。  
会议先形成结论，再补证据链接，后续没人能判断“这个结论是强证据还是弱共识”。

第三类失败是完成态漂移。  
讨论结束后没有明确 handoff 去向，团队把“说清楚了”误当成“可以执行了”。

### 3) 一个可用答案：把讨论系统化为可验证交接

可执行答案不是“写得更完整”，而是把讨论改造成可验证交接系统。

最低要求是四件事同时成立：
- 信息可继承；
- 分歧可收敛；
- 结论可验证；
- 结果可交接。

如果四者缺一，讨论就会在下一轮重新开始。

## 二、机制设计

### 1) 四个模块职责要稳定且可自解释

`input_and_qa.md` 负责边界与澄清，防止问题定义漂移。  
`finding_and_analyze.md` 负责选项与权衡，防止决策理由丢失。  
`expert_forum.md` 负责争议与证据，防止收敛过程不可复核。  
`outcome_and_handoff.md` 负责去向与责任，防止执行接口断裂。

一个简单判断标准：把文件名单独贴给陌生协作者，他是否能在 10 秒内知道这个文件负责什么。

### 2) 论坛收敛机制必须先证据后结论

关键分歧必须在同一场域关闭，否则会出现“会内结论 + 会外改写”的双轨系统。

`lightning_talk_forum` 的实践顺序：
1. 每位专家先陈述观点与风险。
2. 每位专家给出最关键参考并说明映射关系。
3. 专家交叉评分后再给结论。

例如本次样本重写中，结构专家给出“标题独立表达”规则，叙事专家补充“功能性转折词”，红队专家要求“用户评判入硬门禁”。三者先独立发言，再交叉评分，最后合并为统一改稿约束。

### 3) 实验验证机制要同时回答两个问题

MVP 不是“先做一点看看”，而是“最小成本验证两个维度”：
- 观点是否成立；
- 工具是否可用。

本轮实验的可操作定义：
- 观点成立信号：改稿后是否能把“问题-机制-执行”链条写清。
- 工具可用信号：脚本是否能复现检查结果，并证明源文未被修改。

因此我们强制实验隔离：所有改动仅在 `experimental/`，源文不可写。

## 三、运行闭环

### 1) 完成态必须是执行接口，不是讨论情绪

完成态至少包含三项证据：
- 结论可检索（frontmatter）；
- 评审状态明确（含用户评判）；
- handoff 去向可追踪（action/memory/archive）。

这三项里任意一项缺失，都应判定为“仍在讨论态”。

### 2) 归档要回答“谁接、接什么、如何追溯”

归档记录不只是留痕，而是交接契约。

一条可用归档记录应至少包含：
- source artifact 与 archived artifact；
- action handoff 目标与路径；
- memory handoff 目标与路径；
- gate 检查结果（是否满足 completion）。

没有这些字段，后续复盘只能靠聊天记录回忆。

### 3) 最小案例：从平铺讨论到可执行交接

Before（平铺）：
- “我们觉得这篇写得不行，要更有结构。”
- “先改一下再看看。”

After（可执行）：
- 问题定义：标题层级不足，读者无法定位主论点。
- 改动规则：二级标题固定 4 块，三级标题承载诊断/机制/证据。
- 验证信号：`v5` 结构检查通过，用户评判状态可追踪。

从“意见”到“接口”的变化，才是系统收益。

## 四、落地与边界

### 1) 建议上线顺序

先稳接口，再扩能力：
1. 固定文件契约（四模块）。
2. 固定论坛门禁（证据、评分、用户评判）。
3. 固定实验隔离与归档格式。
4. 最后再扩文体 profile。

顺序反过来，团队会在高复杂流程里重复基础错误。

### 2) 哪些场景不适合硬门禁

对于强创意、弱验证任务（例如纯概念发想），部分规则应降级为指导项。

但只要任务要进入多人执行链路，至少要保留“证据顺序 + handoff 去向 + 评判状态”三项硬约束。

### 3) 下一步迭代建议

下一步建议聚焦两个增量：
- 统一“观点成立/工具可用”实验报告模板；
- 在不破坏核心契约下扩展 `bagakit-paperwork-xxx` 文体 profile（blog、RFC、postmortem）。

## 结语

代码解决局部正确性，项目管理解决持续正确性。

当任务跨会话、跨角色推进时，决定上限的不是单次表达能力，而是系统是否能稳定保存、验证并交接决策。
