# Brainstorm 的自解释系统与专家论坛评审系统

> Coding 的尽头是项目管理

## 问题陈述

团队并不缺想法，缺的是可继承的决策过程。

在复杂项目里，brainstorm 经常在会议中看起来“讨论充分”，但进入执行阶段就失效：下一轮成员无法判断上轮到底决定了什么、哪些假设已经验证、哪些结论仍在争议中。这类失败通常不会在会议现场暴露，而会在交接时集中出现。

如果系统不能跨轮次保存“决策身份”和“证据顺序”，讨论越多，执行成本通常越高。

## 为什么即使强团队也会在这里失效

经验丰富的团队同样会失效，因为问题不在个人能力，而在机制缺口。

我们在实践里反复看到三类失败模式：

1. 结构漂移：每次讨论都重新命名阶段，导致历史不可复用。
2. 证据漂移：观点先定，证据后补，最后无法判断结论强度。
3. 完成态漂移：讨论结束被误认为任务完成，但 handoff 去向并不明确。

这些失败模式有一个共同点：都发生在“流程交界处”，而不是单次发言质量上。

## 这个问题可以拆成四个机制

这个问题可以拆成四个独立但互锁的机制：连续性、收敛性、验证性、交接性。

### 1) 连续性：保证上下文可继承

连续性要求每轮都在同一文件契约上工作，而不是临时组织内容。

- `input_and_qa.md`：记录问题边界与澄清结果。
- `finding_and_analyze.md`：记录选项、权衡与决策矩阵。
- `expert_forum.md`：记录争议、证据、评分与结论。
- `outcome_and_handoff.md`：记录执行去向与风险控制。

文件名必须脱离上下文也可自解释，这是跨会话协作的最低条件。

### 2) 收敛性：把争议放进一个场域

收敛性要求关键分歧只能在 `expert_forum.md` 里关闭。

论坛模式可以不同，但规则应一致：先证据、后观点；先互评、后结论。对于开放问题，`lightning_talk_forum` 先快速覆盖观点，再决定是否进入 deep-dive，会比一开始就深挖更稳健。

### 3) 验证性：把“说服力”替换成“证据力”

然而只有论坛还不够。没有实验，讨论往往会回到修辞竞争。

最小 MVP 的目标不是做大，而是回答两个问题：
- 观点是否成立；
- 工具是否可用。

因此实验需要强约束：所有改动只能写入 `experimental/` 目录，源文不可直接修改。只有这样，实验结果才具备审计价值。

### 4) 交接性：把“讨论完成”变成“执行就绪”

讨论完成不等于任务完成。

一个可执行完成态至少包含：
- 结论已写入 frontmatter，可被定位和复核；
- `discussion_clear` 与用户评判状态明确；
- action/memory handoff 去向明确，并可归档追踪。

缺少其中任意一项，都应视为“仍在讨论态”。

## 实施顺序

给定上述机制，一个更稳妥的落地顺序是：

1. 先固定文件契约，消除命名漂移。
2. 再启用论坛门禁，消除旁路决策。
3. 最后引入 MVP 与归档约束，提升证据强度。

这个顺序的核心是先稳定协作接口，再提高讨论上限。

## 边界与后续工作

这套系统主要服务于技术决策与工程写作场景。对于强创意、弱验证的任务，部分门禁应降级为指导性约束，而不是硬门禁。

后续工作有两项：

1. 把“观点成立/工具可用”的实验结果抽象成统一报告格式；
2. 为不同文体建立可选 profile（例如 blog、RFC、postmortem），在不破坏核心契约的前提下扩展表达风格。

## 结语

代码解决局部正确性，项目管理解决持续正确性。

当问题跨越多个会话和多个角色时，真正决定效率上限的不是一次写出多少内容，而是系统是否能稳定地保存、验证并交接决策。
